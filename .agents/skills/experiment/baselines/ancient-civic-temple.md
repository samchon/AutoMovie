### 원인 확정 — 등록 방식이다 (한 턴 안의 대조군)

**MCP 결과를 `invocation.server`로 그룹핑하면 답이 나온다.** 두 드라이버 모두 처음에는
**합계로만** 세었고, 그래서 둘 다 자기 데이터를 잘못 읽었다.

턴 1, **같은 턴·같은 `approval_policy: "never"`·같은 `approvals_reviewer: "user"`**:

| 서버 | 등록 방식 | ok | err |
| --- | --- | --- | --- |
| `automovie_ancient` (샌드박스 제품 표면) | **호출 단위** (`-c mcp_servers…`) | **0** | **3** |
| `node_repl` | **전역** (`~/.codex/config.toml`) | **27** | **0** |

**다른 것은 등록 방식 하나뿐이다.** 두 머신을 비교한 것이 아니라 한 턴 안의 대조군이다.

형제 세션(`modern-suburban-house`)도 **같은 정정을 독립적으로 냈다** — "MCP 3건 성공"은
`node_repl`이었고 **제품 표면에 대해서는 0/3**이었다. 두 세션이 이제 **일치한다.**
"형제가 재현하지 못했다"는 예외는 **애초에 존재하지 않았고, 합계로 센 탓이었다.**

| 등록 | reviewer | 결과 | 근거 |
| --- | --- | --- | --- |
| 호출 단위 | `user` | **거절** | 턴 1 `automovie_ancient` 3/3, 폐기 세션 A·C |
| 호출 단위 | `auto_review` | **성공** | 폐기 세션 B·E |
| 전역 | `user` | **성공** | 턴 1 `node_repl` 27/27 |

**호출 단위 등록 서버는 승인을 요구하고, 전역 등록 서버는 요구하지 않는다.**
`policy=never` + `reviewer=user`면 그 요청이 자동 거절된다.

**운영 결론.** 격리를 지키려면 호출 단위 등록이 필요하고, 호출 단위 등록은 승인
게이트를 부른다. 따라서 **`-c approvals_reviewer="auto_review"`는 필수다.**

죽은 후보: `approvals_reviewer` 값 차이, `network_access`, 첫 호출 vs resume,
`approval_policy="on-request"`. **`#1992`(모듈 스코프 `os.userInfo()`)도 원인이 아니다** —
세 번째 거절이 저작자의 심 작성 **이후**에 났다. 다만 그 심의 존재 자체가 `#1992`의
독립 증거다.

부수 정정 하나. 아래 4절은 "`--approve-for-me` 모드에서 `npm`이 `PSSecurityException`
으로 막힌다"고 적지만, `auto_review`에서 `npm.cmd --version` → `10.9.4`,
`node --version` → `v22.21.0`이 정상 실행됐다. 그 실패는 승인 모드가 아니라 **`.ps1`
심이 `RemoteSigned`에 막히는 별개 원인**으로 보인다. `npm.cmd`를 부르면 재현되지 않는다.

통과시킨다」는 미확인 항목은 저장소가 이미 측정해 둔 것이고, emitter의 거절이 그 답으로
만들어진 수정이다.** 남는 조건은 하나뿐이다 — **그 거절은 `design`을 돌려야만 나온다.**

#### `#1961` probe 2 — 실행함. 재팩된 현재 제품, scratch 사본 (2026-08-18 16:5x)

`experimental/.probe-1961`에 프로덕션을 복사하고(`renders/` 제외) `node_modules`를
**junction**으로 걸어 모듈 해석을 동일하게 두었다. 락은 프로젝트 루트 경로의 해시로
키가 잡히므로(`rootNamespaceLock.ts:96`) 실제 샌드박스와 충돌하지 않는다. 측정 뒤
**junction을 먼저 rmdir로 떼고** 디렉터리를 지웠다 — 재귀 삭제가 junction을 따라가면
실제 샌드박스의 `node_modules`가 사라진다.

**깨끗한 기준선을 먼저 잡았다** (이것이 없으면 뒤의 결과를 귀속할 수 없다):
`design` exit 0 전부 `unchanged`, `compile` exit 0 / `success: true` / **진단 0**,
리뷰 대상 47 / missing 0.

그 다음 서로만 참조하는 스타터 레코드 5개를 복원했다 —
`shared/models/{soloist,chorus-hero,chorus-near,chorus-far}.json`,
`shared/formations/chorus.json`. (`chorus` → `chorus-hero` → `chorus-{hero,near,far}`,
`soloist` → 자기 자신. 폐집합임을 파일 내용으로 확인했다.)

| | `design` | `compile` 진단 | 리뷰 대상 | missing |
| --- | --- | --- | --- | --- |
| 원본 | exit 0 | **0** | 47 | 0 |
| **+ 고아 5개** | **exit 1, 5개를 전부 이름** | **0 (완전 침묵)** | 48 | **1** |
| 삭제 후 | exit 0 | 0 (정착 후) | 47 | 0 |

**저장소의 주장이 현재 제품에서도 성립한다.** `compile`은 exit 0, `success: true`,
`"diagnostics": []`로 **완전히 침묵**하면서 남의 영화를 `generated/`에 **9개 파일**로
지어 넣었다 — `contracts/{formations/chorus,models/{chorus-far,chorus-hero,chorus-near,soloist}}.json`
과 `models/*.json` 4개. 삭제하면 9개가 0개로 정리된다.

**`design`만이 그것을 잔재로 이름 댄다** — exit 1, 5개 전부를 프로젝트 상대 경로와
레코드 id와 조치까지. (여기서도 문구는 저작자가 고쳐 쓴 한 문장이었다 — probe 1의
정정이 통제된 조건에서 재현됐다.)

##### 그런데 다른 표면이 그것을 이름 대고, **반대를 말한다**

`lint` / `verify` / `review:status`가 침묵하지 않는다. 복원한 formation이 리뷰 대상으로
**새로 생기고**(47 → 48) `state: "missing"`이 되며, `lint`가 그것을
**`category: "error"`**로 올린다.

```
{
  "code": "review-missing",
  "category": "error",
  "phase": "review",
  "target": "design:formation:chorus",
  "path": null,
  "message": "Review state is missing. Run prepareReview, correct the target, and submitReview before this compile scope. Correction feedback does not authorize deleting the artifact."
}
```

**`design`은 "지워라"라고 하고, 리뷰 표면은 "리뷰해라, 삭제는 허가되지 않는다"고 한다.**
같은 레코드에 대해 두 배송 표면이 반대 지시를 낸다.

**다만 정확히 말해야 한다 — 이것은 고아를 겨냥해 쓴 문장이 아니다.**
`AutoMovieProductionReviewService.ts:3197`의 `appendReviewCorrectionSafety`가 그 문장을
**모든 리뷰 진단에 무조건 덧붙인다**(이미 있으면 건너뛸 뿐). 의도는 명백히
"리뷰 피드백은 고치는 대신 지워도 된다는 허가가 아니다"라는 안전장치다.
그러므로 주장은 「제품이 자기모순이다」가 아니라 이것이다 —
**포괄 안전 접미사가 그것을 위해 쓰이지 않은 경우에 도달하고, 그 경우에 emitter 자신의
조치와 충돌한다.**

##### 남는 비대칭

고아 5개 중 **리뷰 표면이 이름 댄 것은 formation 하나뿐**이다. 모델 4개는 리뷰 대상이
되지 않았다. 즉 "design 말고 다른 것이 이름 대는가"의 답은 **부분적으로 그렇다**이고,
그나마 잔재로서가 아니라 **떠안아야 할 의무로서**다.

#### 새로운 오염 형태 — 형제 저장소 에이전트가 샌드박스에 손으로 써 넣는다

핸드오프 11절은 공유 checkout의 **브랜치 이동**이 tracked 편집을 지운다고 적었다.
이번에 잡힌 것은 반대 방향이다: **저장소 쪽 에이전트가 자기 진행 중 변경을 내 샌드박스에
복사해 넣었다.**

설치된 tarball 스캐폴드와 다르면서 **저장소 작업 트리와 바이트 동일한** 샌드박스 파일이
정확히 셋이다.

| 파일 | 샌드박스 mtime | 대응 커밋 |
| --- | --- | --- |
| `viewer/src/film.ts` | 14:12:43 | `85888669` #2002 (14:02:44) — 무해 |
| `viewer/src/subject.ts` | **14:42:11** | `f4fd388e` #2009 (15:02:56) |
| `viewer/subject.html` | **14:42:11** | 같은 커밋 |

뒤의 둘은 **32 ms 차이**로 들어왔고 #2009이 바꾼 파일 **정확히 그 둘**이다. 그 변경은
engine `#2005`(`4a2ea0e8`, 14:33)의 세 번째 인자를 요구하는데 **이 샌드박스의 engine
tarball은 09:29 팩이라 그것이 없다.** 결과가 실측됐다 — 06:59:27Z에 `npm run lint:source`가
exit 2로 죽는다.

```
viewer/src/subject.ts:551:61 - error TS2554: Expected 2 arguments, but got 3.
    answer = describeAutoMovieSubject(artifact, compiledId, { memberOffset });
```

**저작자가 쓴 파일이 아니다.** rollout 4,258줄 전체에서 `viewer/` 아래를 겨눈
`apply_patch`가 **0건**이고, 저작자의 유일한 viewer 접촉(03:51:46Z)은 **설치된 tarball
스캐폴드에서 샌드박스로 되돌려 복사**하는 방향 — 즉 2인자 판을 쓰는 쪽이다. 저작자 자신도
06:59:49Z에 *"That file is outside the production source I changed"*라 적었고, 턴 4
체크포인트에서 *"I did not author or overwrite that file"*로 다시 적었다.
**독립적으로 같은 결론에 도달했다.**

**제품 결함이 아니다.** 저장소 CI에 `internals/scaffold-evidence-gate.mjs`가 있고, 그것은
스캐폴드 `tsconfig.json`의 `include`를 **통째로**(`viewer/src` 포함) 빌드된
`packages/*/lib/index.d.ts`에 대고 컴파일하며, 두 커밋이 올바른 순서로 착지했으므로
저장소는 일관됐다. **실행의 조건으로 기록한다** — 그리고 이것이 「샌드박스가 저장소 안에
살면 자기 실험과 무관한 이동을 겪는다」의 **세 번째 형태**다: head 이동, 브랜치 이동,
그리고 **남의 손 패치**.

**교훈이자 값싼 계측.** 샌드박스 파일을 **설치된 tarball 스캐폴드**와 대조하면 이것이
한 번에 보인다. `node_modules/automovie/scaffold/**`는 그 프로젝트가 무엇으로
태어났는지에 대한 **저장소와 무관한 기준선**이고, 거기서 벗어난 파일은 저작자 아니면
침입자다. 저장소 작업 트리와 대조하는 것으로는 이것을 가릴 수 없다 — 침입자의 출처가
바로 그 작업 트리이기 때문이다.

#### 부수 — 재팩이 **행동으로** 확인됐다 (`#1998`, 관사)

S2 시점에 내가 그대로 옮겨 적은 gap의 reason은 이랬다.

> "**a** opening row states type, size and count but no place, …"

재팩 뒤 같은 필드가 이렇게 읽힌다.

> "**an** opening row states type, size and count but no place, …"

`#1998`(`withArticle` — 진단이 이름 대는 값에서 관사를 유도한다)이 실제 산출물에서
바뀐 것이다. **grep으로 패키지 안을 본 것이 아니라 제품 출력이 달라진 것을 봤다** —
잔류 확인의 더 강한 형태다.

**방법상의 요점.** 이 전후 비교는 계획된 것이 아니었다. S2에서 gap 텍스트를
**요약하지 않고 그대로 인용해 둔 것** 하나 때문에 성립했다. 서술로 적어 두었다면
("개구부 위치 gap이 있다") 관사 변화는 흔적도 남지 않았을 것이다.
**인용은 나중에야 값이 드러나는 종류의 기록이다.**

#### 세 신호의 정정 — **rollout 성장은 생존이지 생산이 아니다** (쿼터 소진, 실측)

Codex 계정이 주간 한도를 소진했을 때 세 신호는 이렇게 읽혔다.

| 신호 | 값 | 순진한 판정 |
| --- | --- | --- |
| 프로세스 | root `codex.exe` 6564 **살아 있음** | alive |
| rollout | 20,869,241 → 20,951,236 (**자람**) | alive |
| 디스크 | 5분간 **0건**, revision **422에 고정**, 프레임 **160에 고정** | **stalled** |

**셋 중 둘이 살아 있다고 말하는데 생산은 0이었다.** rollout이 자란 것은 작업이 아니라
**재시도 잡음**이었다 — 그 구간에 `429` 14건, `rate_limit` 34건, `usage limit` 3건이
쌓였다. rollout에 실린 것은 진행이 아니라 거절이다.

쿼터 서명은 rollout 안에 그대로 있다.

```json
"rate_limits": { "limit_id": "codex",
  "primary": { "used_percent": 100.0, "window_minutes": 10080, "resets_at": 1787196801 },
  "credits": { "has_credits": false, "unlimited": false, "balance": "0" },
  "plan_type": "pro" }
```

**그러므로 세 신호 규칙을 이렇게 좁힌다.** 프로세스와 rollout은 **세션이 살아 있는가**를
답하고, **디스크만이 일이 되고 있는가**를 답한다. 턴이 끝났는지에는 셋이 필요하지만,
**진행 중인지에는 디스크가 권위**다. 기준선이 "크기를 보라, mtime을 보지 말라"고 적은
것은 여전히 옳지만 충분하지 않다 — **자라는 크기도 거짓말할 수 있다.**

세션은 스스로 종료했다(root 6564 소멸). **아무것도 죽이지 않았다.**

##### 부수 — 죽은 세션이 캡처 브라우저를 고아로 남겼다

root가 사라진 뒤에도 `node.exe` PID 42024(18:08:36)와 그 자식 `chrome.exe` **5개**가
내 샌드박스 경로를 달고 살아 있었다. 핸드오프가 적어 둔 위험이 바로 이것이다 —
**고아 캡처 러너들이 같은 상태를 놓고 경합하다가 캡처가 아무 말 없이 멈춘다.**
지시에 따라 죽이지 않았고, **다음 저작자의 캡처가 멎으면 첫 번째 용의자로 기록**한다.

#### 함정 5의 반대 방향 — 알림이 **나쁜 소식**으로 왔다 (실측, 턴 5)

기준선은 완료 알림을 **"좋은 소식의 얼굴로 온다"**고 적었다 — 끝나지 않은 턴에 대한
`completed`. 턴 5에서 같은 함정이 **반대 얼굴로** 왔다.

```
task b11oqnbep  status: killed   "Send turn 5 checkpoint to authoring session" was stopped
task bzzw3gkgu  status: killed   "Arm boundary watcher on turn 5" was stopped
```

**둘 다 내 래퍼였고, 세션은 멀쩡히 일하고 있었다.** 그 시각 세 신호:

| 신호 | 값 | 판정 |
| --- | --- | --- |
| 프로세스 | root `codex.exe` PID 6564 살아 있고 `CreationDate 17:16:46` 일치 | **alive** |
| rollout | 20,827,075 → 20,830,410 (13초) | **alive** |
| 디스크 | 3분 내 2건, revision 420 → **422** | **alive** |
| 래퍼 stdout | 로그 **9.7 MB**, mtime이 7초 전 | **리다이렉트 생존** |

`completed`를 턴 종료로 읽으면 살아 있는 스레드에 다음 턴을 쏴서 `thread-store conflict`를
얻는다. **`killed`를 읽으면 더 나쁘다 — 세션 사망을 기록하고 망가지지도 않은 것에 대한
복구를 시작한다.** steering.md가 두 결과를 나란히 예고했고, 이 사이클이 **두 번째 쪽을
실측했다.**

**교훈은 강화된다: 알림은 어느 방향이든 신호가 아니다.** 좋은 소식이든 나쁜 소식이든
세 신호와 일치하거나 틀린 것이고, 여기서는 틀렸다. **복구할 것은 없었다** — 워처만 다시
걸면 된다(래퍼가 reap돼도 exec된 프로세스가 리다이렉트를 유지한다).

##### 곁들여 — `turn_context` 개수를 턴 개수로 읽으면 안 된다

같은 순간 `turn_context`가 6 → 7로 늘었다. **새 턴이 아니다.** #6과 #7이 turn_id
`01a013f1-c6d3-7923-bef0-4a1c1007eda1`을 **공유**한다 — 한 resume 안의 내부 연속이고,
턴 3에서 #3·#4가 보인 것과 같은 형태다. **turn_id로 묶어 세지 않으면 살아 있는 턴을
끝난 것으로 센다.**

##### 그리고 내 파서가 또 그럴듯한 빈 값을 냈다

turn_id를 뽑는 파서가 **아무것도 출력하지 않았다.** `turn_context` 줄은 `type`을
**최상위**에 싣는데 내가 `payload.type`으로 걸렀기 때문이다. 그 침묵은
"turn_context가 없다"와 구별되지 않는다. **grep이 7이라고 말해 둔 것 하나 때문에**
파서를 의심할 수 있었다. 기준선의 함정 3과 같은 형태이고, 규칙도 같다 —
**입력 개수를 먼저 말하게 하고, 0을 결과가 아니라 고장으로 읽는다.**

### 발견 가능성 실행에서 **제품의 에러 텍스트는 조종 재료가 될 수 없다** (이 사이클이 산 규칙)

`briefing.md`는 **내가 쓰는** 모든 메시지에서 도구 이름을 빼라고 요구한다.
빠져 있던 것은 **내가 쓰지 않는 메시지**다.

probe 2가 찾아낸 리뷰 진단의 본문은 이렇다.

> "Review state is missing. **Run prepareReview, correct the target, and submitReview**
> before this compile scope. Correction feedback does not authorize deleting the artifact."

이것은 발견이었고 저작자에게 보낼 이유도 있었다 — 같은 레코드에 대해 `design`과
반대되는 지시를 내는 표면이기 때문이다. **그런데 그 발견을 서술하는 행위 자체가**
이 실행이 재려고 존재하는 이름 셋 중 **둘을 인용으로 넘긴다.**

**그러므로 규칙은 두 겹이다.**

1. 내가 쓰는 문장에서 이름을 뺀다 (기존).
2. **제품이 쓴 문장을 인용해서도 안 된다.** 진단·거절·remedy 텍스트는 도구 이름을
   자기 안에 싣고 있으므로, 발견 가능성 실행에서 **제품 출력은 조종 재료가 아니다.**

**따라서 그 텍스트에 관한 finding은 저작자에게 알릴 것이 아니라 드라이버가 발행할
것이다.** 턴 5에서 나는 그 스레드를 통째로 들어냈고, 저작자에게는 `place` 철회와
재팩 통보만 보냈다.

**정직하게 적어 둘 것.** 송신 전 정규식 스캔이 0을 냈지만, **0을 만든 것은 스캔이
아니라 인용을 먼저 들어낸 판단이다.** 스캔은 이미 지운 것을 확인했을 뿐이다.
계측기가 통과를 보증한다고 읽으면 다음번에 인용이 그대로 실려 나간다 —
이 기준선의 「그럴듯하게 실패하는 계측기」 가족과 같은 형태다.

(감독관이 `briefing.md`에 `#2031`로 반영했다.)

### 제품 결함 후보 — `opening-location`/`connector-location`이 저자에게 불가능한 조치를 지시한다

**S2의 마지막 gap을 쫓다가 나왔다.** 개구부 16개의 `place`가 전부 `null`이고, 제품이
그것을 gap `opening-location`, **`status: "not-run"`**, remedy
*"resolve the opening's host boundary to the spaces it separates, **then fill the row's
place**"*로 선언한다. 저작자는 그 조치를 거부하며 *"the schedule schema does not project
them. I did not invent a parallel schedule"*라고 적었다. **저작자가 옳다.**

**코드 경로 (`packages/engine/src/drawing/drawingSchedule.ts`).**
`openingOccurrences`와 `connectorOccurrences`의 **모든 return 8개가 `place: null`을
하드코딩**한다 (416, 433, 447, 455행 및 480, 497행 등). 개구부·커넥터의 `place`를
채우는 코드 경로가 **존재하지 않는다.** 반면 space 행은 280행에서 실제로 채운다 —
필드가 死文이 아니라 **subject에 따라 갈린다.**

**타입 계약이 이것을 오분류로 판정한다** (`IAutoMovieDrawing.ts`).

| 요소 | 계약 문구 |
| --- | --- |
| `AutoMovieDrawingGapStatus` | *"Whether a derivation is **missing entirely** or merely **had nothing to run on**."* |
| `status` | *"Whether the derivation **does not exist** or merely **had no input**."* |
| `remedy` | *"Exactly what would make the derivation produce a result."* |

엔진 자신의 주석이 205–208행에서 **"that derivation is not written"**이라고 적는다 —
즉 derivation이 **존재하지 않는다**. 계약대로면 `unsupported`다. 그런데 `not-run`으로
나가고, `remedy`는 **저자에게** 말을 건다. 저자는 그것을 만족시킬 수 없다.

**같은 함수가 같은 어휘를 두 번은 옳게 쓴다.** `opening-performance`는 `unsupported`이고
remedy가 실제로 저자 행동이다("author the opening's operable state…").
`traversal-performance`도 `unsupported`이고 remedy가 제품을 향한다("run a traversal
analysis **once one exists**"). **셋 중 하나만 어긋난다.**

**도달 범위.** `subject !== "space"`인 모든 스케줄 — 즉 개구부나 커넥터를 가진
**모든 프로덕션**. 이 샌드박스에서 개구부 16 · 커넥터 8, revision 359에서 실측.

**비용이 실재한다.** 저작 세션이 S2 종료 시점에 이것을 만나 턴 시간을 쓰고, 옳게
거부한 뒤 unmet으로 기록했다. 덜 신중한 저자는 채울 수 없는 필드를 쫓는다.
브리프가 S2 gap을 닫으라고 요구하기 때문이다.

**관측자의 가설로 적는 수정 방향.** `status`를 `unsupported`로 바꾸고 remedy를 제품을
향하게 하는 것(`traversal-performance`의 문형)이 계약과 일치한다. 다만 요구사항이
"모든 subject가 location을 답한다"이므로, 진짜 답은 derivation을 쓰는 것일 수도 있다.
**어느 쪽인지는 이 실험이 판정할 것이 아니다** — 오분류만이 측정된 것이다.

**이 기준선을 읽었다.** 이전 저작자의 S1–S3 상태와 체크포인트, probe 결과, `#2029`와

Codex에서 그 벡터가 닫혀 보였던 것은 Codex의 실제 열람 범위가 좁게 유지됐기 때문이지

**그러나 파일을 옮기는 것이 해법이 아니다.** tracked·저장소 안이라는 것이 이 파일이
샌드박스보다 오래 사는 이유이고, 그것이 존재 이유 전부다. 알려진·기록된 오염을
런 중간에 **미지의 내구성 손실**과 맞바꾸지 않는다.

**다음 사이클의 셋업 요구사항으로 적는다.** 레거빌리티를 재려면 **열람 루트에 이 저장소가
아예 없는 샌드박스**가 필요하다 — **그리고 그 저장소의 이력도 없어야 한다.**

형제 샌드박스(`future-citizen-house`)가 **같은 부류의 두 번째 벡터**를 찾았고, 그것이 이
발견을 반복하는 것이 아니라 **넓힌다.** 그쪽 에이전트는 드라이버 노트를 **한 글자도 읽지
않았고**(노트 고유 마커 전부 0건) 그런데도 **캠페인 커밋 제목 22개를 받았다** — 부모

결과였다. 즉 파일을 읽지 않아도 **이력이 같은 것을 말해준다.**

**따라서 격리 조건은 파일 트리가 아니라 저장소 전체다** — 작업 트리와 `.git` 양쪽. 파일 하나의 위치가 아니라 **사이클을 어떻게 세우는가**의
문제다. 그 배치 없이는 이 축을 측정했다고 말할 수 없다.

#### 프로세스 귀속 — Claude Code에서는 **MCP 서버가 유일한 앵커다**

턴 2를 띄운 뒤 머신에 `claude.exe`가 **7개** 있었고, **그중 내 절대경로를 커맨드라인에

싣지 않는다. Codex의 resume 턴이 UUID를 실었던 것과 다르다 — **하네스마다 어느 신호가

```
node.exe(21304) <- node.exe(20160) <- claude.exe(5732) <- sh.exe(24636)
                                      ^^^^^^^^^^^^^^^^ 내 루트 (19:16:36)
```

**즉 이 하네스에서 세션을 식별하는 것은 세션 자신이 아니라 그것이 띄운 제품 서버다.**
그리고 트랜스크립트 파일은 UUID로 명명되어 충돌하지 않으므로(Codex rollout과 같은 성질)
**세션 정체의 1차 증거는 트랜스크립트, 프로세스 귀속의 앵커는 MCP 서버**로 나눈다.

```
  'offering' 242회 · 'jar' 29회 · 'table' 14회 · 'fountain' 68회 · 'basin' 14회
```

**정면 외관 샷의 계약이 실내 봉헌실 가구를 통째로 싣고 있다.** 12개 계약이 전부 약 155 KB로
거의 같은 크기다. 즉 샷 계약은 *그 샷이 무대에 올리는 것*이 아니라 **건축 환경 전체**를
물질화한다.

**측정된 비용.** 리뷰 staleness가 계약 digest에서 계산되므로, 어느 방의 내용물이든 바뀌면
**모든 샷의 리뷰가 무효가 된다** — 실내 가구를 보여줄 수 없는 외관 입면까지. 저작자가
**두 라운드 연속** 그 선택에 부딪혔고 두 번 다 같은 이유로 미뤘다: 픽셀이 움직이지 않았다.
현재 52개 대상 중 **21개 stale**이고, 그 대부분이 그 계단식 무효화다.

**반례가 존재하므로 보편 성질로 적지 않는다.** steering.md는 다른 프로덕션에서
**커튼월 하나가 222개 중 22개만 움직였고 움직인 샷은 그것을 마주 보는 둘뿐**이었다고
기록한다. 그러므로 이 전(全)-샷 계단식은 **이 배치의 성질이지 제품의 상수라고 말할 수 없다.**
두 형상이 무엇 때문에 갈리는지는 이 실험이 정할 것이 아니다.

**정직한 주장은 여기까지다.** (a) 이 프로덕션에서 샷 계약은 환경 전체를 싣는다 — 실측.
(b) 그래서 무관한 샷의 리뷰까지 stale이 된다 — 실측. (c) 그것이 저작자에게 실제 비용을
두 번 물렸다 — 실측. **(d) 그것이 결함인지 결정론적 캡처를 위한 자족적 계약의 대가인지는
미확정이다.** 후자라면 고칠 곳은 계약이 아니라 **staleness가 무엇을 키로 삼는가**일 수 있다.

#### 어느 계측기가 질문을 끝내는가는 **질문에 달렸다** — 한 건물에서 양방향 실측

이 프로덕션이 같은 라운드 안에서 두 방향을 다 냈다. **쌍으로 적는 이유는 어느 한쪽만
기억하면 반대쪽에서 틀리기 때문이다.**

| 사례 | 프레임이 한 것 | 스윕/수치가 한 것 | 결론 |
| --- | --- | --- | --- |
| **수반 (S4 첫 시도)** | **유일하게 잡았다** — 원기둥 3개를 쌓은 첫 설계가 뚜껑 덮인 드럼으로 읽혔다 | 컴파일도 카운트도 침묵. 진단 0 | **기하가 "무엇으로 보이는가"는 프레임만 답한다** |
| **탁자·항아리 (S4 둘째)** | **끝내지 못했다** — 겹침을 *의심*하게 했을 뿐 | 엔진의 support·placement-overlap 스윕이 **서쪽 벽 안에 0.3 m 박힌 것**과 jamb/sill 교차 **부피 7–38%**를 냈다 | **"안에 있는가 가까이 있는가"는 수치만 답한다** |

저작자 자신의 근거가 정확하다 — *"a wide shot reads that as 'close to the wall' rather
than 'inside it'"*. **넓은 샷에서 벽 안과 벽 옆은 같은 픽셀을 만든다.**

**규칙.** 질문이 *보이는 방식*(가려짐·읽힘·형상)이면 프레임이 권위이고 수치는 침묵한다.
질문이 *위치 관계*(관통·지지·간격)면 수치가 권위이고 프레임은 그럴듯한 오답을 준다.
**프레임을 한 장 더 보는 것으로 두 번째 부류를 끝내려는 시도가 이 캠페인이 반복해서
치른 비용이다.**

싼 쪽 판단도 같은 규율이다: 저작자가 turntable 프레임의 어두운 쐐기를
**"확인에 예산을 쓰지 않겠다"고 말하면서** 남겼다. 쫓지도 숨기지도 않는 것이 세 번째 선택지다.

#### 정정 — 계단식 무효화의 원인은 계약이지 staleness 규칙이 아니다

앞 절에서 나는 **"고칠 곳은 계약이 아니라 staleness가 무엇을 키로 삼는가일 수 있다"**고
적었다. **그 추측은 틀렸다.** 감독관이 `productionRenderTargetFingerprint`를 읽었다:
그것은 이미 **샷에 대해 가능한 한 좁다** — `generated.files`를 그 대상 자신의
`shots/<id>.json` 하나로 걸러 그 digest만 해시한다.

그러므로 사슬은 완전히 결정되어 있다: **element 하나 변경 → 모든 샷 계약 변경(각각이 환경
전체를 싣기 때문) → 모든 render-target fingerprint 변경 → 모든 샷 리뷰 stale.**
**좁힐 여지가 없다** — 샷에는 해시할 파일이 정확히 하나이고 그것이 바뀐 그 파일이다.

**내가 이름 대지 못한 세 번째 선택지가 진짜다:** 자족적 계약이 결정론적 캡처의 대가라면,
다시 볼 것은 계약도 fingerprint도 아니라 **인용된 프레임이 바이트 동일한 리뷰를
재수행이 아니라 재확인으로 처리할 수 있는가**이다. 저작자가 **두 번** 바로 그 근거로
미뤘고 두 번 다 옳았다는 것이 그 선택지가 실재한다는 가장 강한 증거다.

**방법상의 교훈.** 나는 소스를 읽지 않고 "무엇을 고쳐야 하는가"를 추측했다. 관측은
견고했고(전 12샷 계단식, 외관 계약이 실내 가구를 싣는다) **처방이 틀렸다.**
experiment 스킬이 이슈에 대해 요구하는 것과 같다 — **처방은 가설로 적고 무엇에 기대는지
밝힌다.** 반례를 붙들어 발행을 미룬 판단은 옳았고, 그것이 이슈를 "계약이 너무 크다"에서
**"저 프로덕션은 무엇을 다르게 하는가"**라는 답할 수 있는 질문으로 바꿨다.

#### 다음 재팩에서 기대할 것 (회귀가 아님)

`building:report`의 gap 수가 **space 스케줄마다 1씩 는다.** 새 `space-enclosure` gap이
"방 행이 자기를 둘러싼 boundary에 대해 아무것도 말하지 않는다"를 선언한다.
**정상이다.** 관찰 포인트: 저작자가 그것을 **닫아야 할 과제로 읽는지, 적어둘 선언으로
읽는지** — remedy가 검사가 아니라 **질의**를 이름 대기 때문이다.

#### 저작자가 교훈을 **전이**했다 — 그리고 그 근거를 소스에 적었다

봉헌실에서 벽 관통을 스윕으로 발견한 다음 라운드, 제단을 지을 때 저작자는 **프레임을
믿기 전에** 스윕을 돌린 것이 아니라 **애초에 그 버그가 생기지 않게** 했다.
`civicTempleRearElevation.ts`의 `shrine` 벽 centring을 **소스에서 먼저 읽고** 반벽두께를
미리 뺐다. 스윕은 첫 시도에 0 floating / 0 overlap이었다.

그리고 그 이유를 모듈 JSDoc에 남겼다 (실측, 내가 소스에서 확인):

> The shrine's own rear wall (civicTempleRearElevation.ts, module `shrine`) centres
> itself at innerHalfDepth, so its clear room-side face sits half a wall thickness
> inward of that centreline, **the same arrangement already measured for the offering
> room's left elevation.**

```ts
const NORTH_WALL_CLEAR_Z = D.envelope.innerHalfDepth - D.envelope.wallThickness / 2;
```

**숫자가 아니라 추론을 적었기 때문에 그것은 저작자보다 오래 산다.** 이것이 캠페인이
드라이버에게 요구하는 「어떻게 얻었는지를 붙여라」와 같은 규율이 **저작 소스 안에서**
성립한 사례다.

같은 턴에 하나 더: 리뷰 슬롯을 **지난 라운드의 패턴에서 추정하지 않고 큐에 물었다.**
지난번엔 2개였는데 이번엔 1개였고, 물었기 때문에 1개만 했다. **자기 색인이 아니라 모델에게
묻는다**가 저작자 쪽에서 독립적으로 나온 것이다.

#### 내 계측기 실패 #4 — **관례가 금지한 곳을 뒤져서 얻은 그럴듯한 부재**

저작자가 보고한 제단 치수(1.0 × 1.6 × 0.6)를 제단 모듈에서 grep했더니 **0건**이었고,
한순간 불일치로 보였다. **내 comparand가 틀렸다.** 이 프로덕션은 치수를
`civicTempleDimensions.ts`에 **중앙집중**하므로, 소비 모듈에 리터럴이 있으면 그것이야말로
결함이다. 실제 값은 제자리에 있었다 — plinth 1.0 × 0.55 × 0.6, stele 1.05,
합성 bounds가 정확히 **1.0 × 1.6 × 0.6**.

**이 실패형의 서명:** 코드베이스의 관례가 "여기엔 없다"를 보장하는 파일을 뒤지면
**검색은 성공하고 결과는 0이며 그 0이 반증처럼 읽힌다.** 앞의 세 함정과 달리 계측기가
고장난 것이 아니다 — **맞게 돌았고 잘못된 곳을 봤다.**
규칙: **부재를 주장하기 전에 그 값이 이 프로젝트의 관례상 어디 사는지 먼저 정한다.**
(기준선이 이미 적어둔 「부재를 주장하기 전에 `docs/`를 읽는다」의 소스 판본이다.)

#### 프로덕션 관측 — **딜리버리 카메라가 핏아웃 없는 건물을 위해 구성됐다**

S4가 진행되면서 지어진 것이 **전달되는 프레임 밖**에 착지하는 일이 두 번 반복됐다.

| 지은 것 | 어디에 있나 | 그 샷의 구성 의도 |
| --- | --- | --- |
| 중정 수반 | 중정 샷 **하단 가장자리** | 신전 쪽을 바라보는 시선 |
| 제단 | 신전 샷 **카메라 뒤** | 입구–중정 sightline 증명 |

**두 카메라 모두 자기 수락 기준을 정확히 만족한다.** 문제는 그 구성들이 **핏아웃이 없는
건물**을 기준으로 정해졌고 이제 핏아웃이 그 뒤로 도착한다는 것이다. 남은 방
(행정·기록·창고·마당)과 식재도 같은 방식으로 착지할 것이다.

**드라이버가 소유한 것과 저작자가 소유한 것을 나눠 보냈다.** 요구(브리프가 각 명명 공간의
내부를 사람이 검토할 거리에서 보게 해달라고 요구하고, 레퍼런스 5장 중 하나가 중정 수반)는
내 것이고, **해법(뷰 추가 / 기준을 여전히 만족하는 구성 변경 / 제3의 것)은 저작자 것**이다.
개별 방마다 답하지 말고 **부류로 한 번에 정하라**고 요청했다 — 그리고 지금 정할지
핏아웃이 더 쌓인 뒤 정할지도 저작자가 고르게 했다.

#### 계측기 실패 #5 — **줄바꿈된 문장은 한 줄 grep에 잡히지 않는다** (거짓 회귀를 발행 직전에 잡았다)

샌드박스의 `AGENTS.md`가 `#1961`의 기제를 산문으로 설명하는 것을 발견하고, 그것이
현재 스캐폴드에 있는지 확인하려고 grep했다 → **0건.** 렌더 시점 커밋
`b545100a`에서도 **0건.** 한순간 **문서 회귀**로 보였다.

**내 grep이 틀렸다.** 이 저장소는 산문을 한 줄에 한 절씩 끊어 쓴다. 그 문장은 이렇게 걸쳐 있다.

```
because nothing downstream can: a resident record that references only other
resident records compiles clean and is built into your `generated` output.
```

`grep -zoE`로 다시 재니 **네 사본 전부에 있다** — 저장소 스캐폴드, 설치된 tarball 스캐폴드,
내 샌드박스, 그리고 `b545100a`. 샌드박스와 스캐폴드의 **유일한** 차이는 `{{name}}` 치환이다.
**회귀는 없었다.**

**서명:** 검색은 성공하고, 대상 파일은 맞고, 패턴도 맞는데, **저장소의 서식 관례**가 0을
만든다. #4(관례가 금지한 파일을 뒤짐)와 짝이다 — 둘 다 **코드베이스의 관례가 만든 거짓 부재**다.
**규칙: 산문에서 구절을 찾을 때는 항상 여러 줄로 찾는다.**

#### `#1961`에 대한 긍정 자료 — 제품 계약이 기제를 **산문으로** 말한다

위 확인의 부수 소득이다. 스캐폴드 `AGENTS.md`는 저작자에게 이렇게 말한다:

> `npm run design` refuses while one is there and names its file, because nothing
> downstream can: **a resident record that references only other resident records
> compiles clean and is built into your `generated` output.** Delete the file it
> names, or derive it.

즉 저작자는 (a) `design`의 거절과 (b) **프로덕션 계약 문서 자체** 양쪽에서 이 기제를 듣는다.
`b545100a` 이후로 계속 있었다. probe 2가 실측한 침묵(`compile` exit 0 / 진단 0 / 남의 영화
9개 파일 생성)이 **문서에 미리 적혀 있는 그대로**였다.

#### 계단식 무효화는 **제품 상수다** — 반례가 해소됐다 (감독관 실측)

내가 붙들었던 반례(커튼월이 222개 중 22개, 마주 보는 샷 둘만)는 **문장 오독**이었다.
네 프로덕션 전부에서 샷 계약 크기를 재니:

| 프로덕션 | 샷 | 계약 바이트 | 프로덕션 내 편차 |
| --- | --- | --- | --- |
| `modern-suburban-house` | 20 | **1,025,819** | ~500 |
| `medieval-baron-manor` | 16 | **724,036** | ~90 |
| `future-citizen-house` | 15 | **276,916** | ~25 |
| `ancient-civic-temple` | 13 | **158,778** | ~100 |

**한 프로덕션 안에서 모든 계약이 반올림 오차 내로 같은 크기다** — 외관 입면과 실내 방 샷이
같은 바이트를 쓴다. 커튼월 사례의 "19 in generated"가 **16개 계약 + 3개**였고,
"두 샷"은 **픽셀이 움직인** 샷 둘이었다. 서로 다른 것을 센 두 문장을 하나로 읽은 것이다.

**그러므로 저작 방식으로 피할 수 없다.** 비용은 샷이 아니라 **건물 크기에 비례**한다.
남은 좁은 질문 하나(계약 안에 그 샷에서 도달 불가능한 것이 실제로 있는가)는 컴파일러의
문제이지 샌드박스의 문제가 아니다.

**방법상 유효한 부분은 남는다:** 반례를 자기 발견에 맞세워 발행을 미룬 것이 질문을
「계약이 너무 크다」에서 **「저쪽은 무엇을 다르게 하는가」**로 바꿨고, 그 질문이 4-프로덕션
측정을 낳았다. **반례가 틀렸어도 반례를 세운 것은 옳았다.**

#### 턴 4 — 저작자가 부류 결정을 **지금** 했고 공짜 이득을 얻었다

미루라고 허용했는데 스스로 지금 하기로 했다. 이유: *"cheaper to fix the pattern at 2
instances than at 6."* 정책을 둘로 정했다 — (1) 기존 카메라의 필수 피사체가 **컴파일러
검증으로** 살아남으면 기울인다, (2) 구조적으로 양립 불가할 때만 보조 샷을 추가하되
**고정 36초 편집에서 명시적으로 제외**한다.

**계획하지 않은 이득이 나왔다.** 중정 카메라를 내려 수반을 잡았더니 **제단이 열린 문을 통해
같은 프레임 배경에 나타났다** — 문이 제단과 같은 축에 있기 때문이다. 내가 프레임을 직접
열어 확인했다: 하단에 물과 분사 하이라이트를 담은 **속 빈 분절 링**, 그리고 문간 안쪽에
**대와 비석**. 두 라운드의 프레이밍 부채가 한 변경으로 갚혔다.

**제품이 저작자의 가정을 네 번 거절했고 네 번 다 옳았다 — 이것은 기록의 나머지 절반이다.**

이 캠페인은 산출의 대부분을 **제품이 잡지 못한 것**에 썼다. 한 턴에 넷을 잡은 실행은
그 반대쪽이고 같은 값어치가 있다. 넷 중 셋은 저작자의 **가정**을 거절했고, 넷째는
저장하는 쪽이 편했을 바로 그 순간에 **낡은 증거를 거절**했다.

| 거절 | 저작자의 가정 | 실제 |
| --- | --- | --- |
| `film-shot-unaccounted` | 등록만 하고 편집에서 빠진 샷이 존재할 수 있다 | **제3의 상태가 없다** — 배치되거나 이유와 함께 명시 생략되거나 |
| `source-registration-mismatch` | 카메라를 고치고 바로 컴파일하면 된다 | `design`이 stale 계약 레코드를 먼저 재도출해야 한다 |
| 같은 것 두 번째 | 소스 모듈만 새 샷을 알면 된다 | **`scripts/emitDesign.ts`도 알아야 한다** — 레지스트리가 둘 |
| 인용 stale | 126행이 `styleIntent`다 | 파일이 밀려 126행은 `scene`이었다 — **서버가 잡았다** |

저작자 자신의 평가: 생략 기제는 *"the right mechanism, not a workaround"*이고
거절이 없었으면 그만큼 확신 있게 찾지 못했을 것이다. **제품의 거절이 저작을 가르쳤다.**

#### 관례가 만드는 거짓 부재 — **두 형태를 규칙으로 고정한다**

계측기 실패 #4와 #5는 같은 가족이고, **둘 다 계측기가 고장나지 않았다.** 맞게 돌았고
코드베이스가 비워 두기로 한 곳을 봤다.

| 형태 | 무엇이 0을 만들었나 |
| --- | --- |
| #4 | 치수를 **중앙집중**하는 관례 — 소비 모듈에 리터럴이 있으면 그것이 결함이다 |
| #5 | 산문을 **한 줄에 한 절씩** 끊는 관례 — 문장이 줄바꿈을 걸친다 |

**규칙 (그대로 적는다):** 산문에서 구절을 찾을 때는 **항상 여러 줄로** 찾는다.
그리고 소스 grep이 0을 내면, **값이 사라졌는지 묻기 전에 이 프로젝트의 관례가 값을
다른 곳에 두는지부터 묻는다.**

#### 턴 5 — 스윕이 진짜 버그 하나를 잡고 거짓 양성 하나를 냈다

**진짜 버그, 프레임을 열기 전에 잡혔다.** 두루마리 통을 선반 상판 높이 + 자기 높이의
절반에 놓았는데, 통 모델의 part가 **이미** 그 오프셋을 내부에 갖고 있다. 이 프로덕션의
고정 관례는 「element Y는 놓이는 높이이고 내부 오프셋은 모델이 처리한다」이고 저작자가
이 한 prop에서만 그것을 깼다. 여덟 개가 전부 0.14 m 떠 있었다. **스윕의
`0.915 m over floor`가 단서였다** — 그 숫자가 실제 여유가 아니라 자기가 잘못 계산한 중심
높이였다는 것을 저작자가 알아봤다.

**거짓 양성, 그리고 받아들이지도 무시하지도 않았다.** 수정 뒤에도 스윕은 여덟 개를 전부
floating + overlap으로 보고했다. 저작자가 이유를 손으로 유도했다 — 선반의 합성 bounding
box가 **등판 때문에 바닥에서 1.8 m까지** 뻗어서, 그 안의 어떤 높이도 box 수준 검사에는
"구별되는 표면"이 아니고 같은 box의 깊이가 판의 얇은 발자국을 삼킨다.

**내가 독립적으로 검증했다 — 세 방식.**

1. **산술.** element Y = `lowerShelfY 0.75 + shelfThickness/2 0.025 = 0.775`,
   통 part의 내부 오프셋 `height/2 = 0.14`, 따라서 통 밑면 `0.915 − 0.14 = 0.775`
   **= 판 윗면 0.775. 간격 0, 관통 0.**
2. **엔진 소스.** `packages/engine/src/architecture/builtEnvironmentPlacement.ts`가
   `builtEnvironmentElementBounds`로 **element 단위 월드 bounds** 하나를 잡고
   *"positive-volume world-bounds overlap"*을 본다. 다부품 모델의 union box가 등판까지
   포함하는 것이 구조적으로 맞다.
3. **프레임.** 기록실 프레임을 직접 열었다 — 통들이 두 단 판 위에 **눈에 보이게 놓여 있다.**
   (덤으로 열린 문 너머 중정 수반이 보인다.)

**관측 — 결함으로 발행하지 않고 후보로 적는다.** 스윕은 설계상 보수적이고 그 사실을
`basis: "element-geometry-bounds"`로 밝힌다. 그러나 그 basis는 **진짜 solid box**와
**대부분이 공기인 다부품 union box**를 구별해 주지 않는다. 그래서 저자는 참 교차와
보수적 거짓 양성을 **출력만으로 가를 수 없고** 손으로 재유도해야 한다.
도달 범위: **다부품 가구 위에 물건을 올리는 모든 프로덕션**(선반·다리 있는 탁자·시렁).
비용은 이 턴에서 실제로 지불됐다.

**저작자의 처신이 옳았다.** 받아들였으면 없는 결함을 고쳤을 것이고, 무시했으면 진짜 관통을
놓쳤을 것이다. **두 독립 검사가 일치했기 때문에** 도구 한계라고 부를 수 있었다 — 이 기준선이
계측기에 대해 요구하는 규율이 저작자 쪽에서 독립적으로 나온 두 번째 사례다.

#### 고리가 닫혔다 — 저작자가 **거부한 지시**가 제품 변경으로 끝났다

이 실행에서 가장 긴 인과 사슬이고, 시작점이 **저작자의 거부**였다는 점이 값지다.

| 시점 | 상태 |
| --- | --- |
| S2 종료 | 개구부 16개의 `place`가 전부 `null`. 제품이 `opening-location`을 **`not-run`**으로 선언하고 remedy가 저자에게 *"then fill the row's place"*라고 지시 |
| 저작자 | **지시를 거부했다** — *"the schedule schema does not project them. I did not invent a parallel schedule."* |
| 드라이버 | 거부를 검증했다. 엔진 row builder의 return **8개 전부가 `place: null` 하드코딩**, space 행만 채운다. **저작자가 옳았다** |
| 발행 | 타입 계약이 오분류를 판정 — `not-run`은 "derivation은 있고 입력이 없다"인데 derivation 자체가 없었다. 같은 함수가 20줄 옆에서 `unsupported`를 **옳게** 두 번 쓴다 |
| 수정 1 | `status`가 `unsupported`로, remedy가 저자가 아니라 제품을 향하게 |
| **수정 2 (최종)** | **gap이 은퇴했다 — 문구 수정이 아니라 제거.** `place`가 subject별 변형을 갖는 discriminated union이 되고 행이 실제 데이터를 싣는다 |

재팩 뒤 내가 직접 읽은 것:

```json
"place": { "kind": "opening", "building": "temple",
           "boundary": "boundary-offering-colonnade",
           "separates": ["colonnade", "communal-offering-room"] }
"place": { "kind": "connector", "building": "temple",
           "stops": ["colonnade", "service-yard"] }
```

`opening-location`과 `connector-location`은 스케줄에서 **0건**이다.
gap 총계는 한 개 들어오고 두 개 나가서 6 → **5**.

**교훈은 관측이 아니라 분업에 있다.** 저작자가 따를 수 없는 지시를 받았을 때
(a) 억지로 따르거나 (b) 조용히 넘기지 않고 **근거를 대고 거부했다.** 드라이버는
그 거부를 중계하지 않고 **소스에서 검증**했다. 그 두 단계가 없었으면 이 사슬은
"저작자가 S2 gap을 안 닫았다"로 기록됐을 것이다.

**드라이버 지침의 「저작자는 증거가 주장보다 약할 때 반박할 것으로 기대된다」가
실제로 산 것이 이것이다.**

#### 재팩 검증 — 16개 머지 (2026-08-19 00:2x)

`lib/*.js`에서 직접: `builtEnvironmentSpaceBoundaries`가 engine lib 3개 파일 +
**컴파일 샌드박스 표면**(`sandboxEngineBridge.js`, `sandboxEngineSurface.js`)에 노출,
`kind: "opening"` 1, `space-enclosure` 1, `opening-location` **0**,
`AUTOMOVIE_COORDINATION_ROOT` 6. tarball 00:23–00:25.

**turn 6 before-side를 재팩 뒤·정착 컴파일 뒤·저작 전에 떴다** (혼동 방지):
revision **472**, 프레임 경로 **172**, 샷 digest **13**, 파생 파일 **188**, src 37.
직전 비교 기준(162 / 12 / 177 @ r430)은 이제 **단계 표식**이지 재팩 비교 대상이 아니다.

**`space-enclosure`는 저작자에게 예고하지 않았다.** 그 remedy가 검사가 아니라 **질의**를
이름 대므로, 저작자가 그것을 *닫을 과제*로 읽는지 *적어둘 선언*으로 읽는지가 관측이다.
규칙: **오독이 턴을 잡아먹으면 미리 알리고, 읽는 방식 자체가 측정이면 알리지 않는다.**
(`generated-stale`은 전자여서 매번 알렸고, 이것은 후자다.)

#### `space-enclosure` 관측은 **아직 발화하지 않았다** — 0을 "무시했다"로 읽으면 안 된다

턴 6 트랜스크립트에서 `space-enclosure` 언급 **0건**. 그것만 보면 *저작자가 선언을
무시했다*로 읽힌다. **틀린 독해다.**

| 측정 | 값 |
| --- | --- |
| 턴 6의 `building:report` 실행 | **0회** |
| 턴 6의 `report.json` 접촉 | **0회** |
| 세션 전체(6턴) `building:report` | 16회 — **전부 재팩 이전** |
| 따라서 저작자가 이 gap을 만난 횟수 | **0** |

**축이 발화하지 않았을 뿐 결과가 null인 것이 아니다.** 이 기준선이 계측기에 대해 세운
규칙(“0은 결과가 아니라 고장”)의 관측 판본이다 — **0은 여기서 고장도 결과도 아니고
‘아직 조건이 성립하지 않음’이다.** 세 상태를 구별해야 한다.

> 만나서 과제로 읽었다 / 만나서 선언으로 적었다 / **만난 적이 없다**

**드라이버가 유도하지 않는다.** 브리프가 이미 매 라운드 룸 스케줄과 카운트를 읽는다고
적어 두었고 저작자는 6턴 중 5턴에서 스스로 돌렸다. 다음 턴에 정상적으로 돌면 그때 발화한다.
gap을 가리키는 것은 측정을 소진시키므로 하지 않는다.

#### 제품이 또 세 번 거절했다 — 그리고 이번 것이 가장 세다

턴 4의 넷에 이어 턴 6에서 셋. **누적 일곱, 전부 옳았다.**

| 거절 | 저작자가 한 것 | 제품이 말한 것 |
| --- | --- | --- |
| 프로토타입 제출 ×2 | evidence `target` 안에 `"kind":"subject"`를 중첩 | 그 자리의 스키마는 `{shot, subject}`만 정의한다 |
| **샷 리뷰 제출** | `acceptance-scenarios`를 **통과로 표시**하면서 필수 시나리오를 실제로 이행하지 않음 | `acceptanceScenarios` id 배열 누락, 시나리오의 **현재 계약을 인용하는 `acceptance` 종 증거** 누락, `completionBasis`가 고위험 쌍(`beat-fidelity`/`representability`)을 **이름으로** 대지 않음 |

**셋째가 스키마 오류가 아니라 「벌지 않은 완료」의 거절이다.** 저작자가
`complete: true`를 냈고 시스템이 *무엇을 근거로 완료라 부르는지*를 물어 거절했다.
그 다음 저작자가 실제 design 레코드를 열어 **그대로 인용**하고 통과했다.
**리뷰 표면이 서류가 아니라 관문으로 동작한다는 가장 직접적인 증거다.**

#### 저작자가 문서 표류를 스스로 잡았다

행정실 산문을 쓰다가 **기록실 선반 문장이 지난 라운드에 `SCN-A03.md`에 들어가지
않았다**는 것을 발견하고 둘을 함께 넣었다. 내가 지적한 것이 아니다. 내가 확인했다 —
현재 `SCN-A03.md`에 shelf/scroll과 desk/chest가 **둘 다** 있다.

**이것이 「산문이 무언가에 답한다」의 논거다.** 빠진 문장은 그 자체로는 보이지 않는다 —
**다른 무언가가 그것이 있어야 할 자리를 가리키기 때문에** 비로소 찾을 수 있다.
증거 그래프가 문서와 소스를 서로 답하게 만드는 이유가 여기서 실물로 나타났다:
저작자는 행정실 문장을 쓰다가 **기록실 문장이 없다는 것**을 알아챘다.
아무도 그 부재를 찾는 일을 배정받지 않았고, 배정할 수도 없었다.

#### 저작자가 내 바이트 동일성 규칙을 자기 쪽에서 적용했다

이번 턴에 beauty 프레임을 **다시 열지 않았고**, digest가 이전에 눈으로 검증한 것과
바이트 동일하므로 그것을 인용했다고 적었다. 내가 「프레임이 바이트 동일한 리뷰는
재수행이 아니라 재확인」이라고 준 규칙을 **증거 인용에까지 확장**한 것이다.
과잉 적용이 아니다 — 무엇을 근거로 재확인인지(digest 동일)를 함께 적었다.

### 세션 내부 대조군 — 이 실험에서 가장 강한 관측

같은 세션의 두 턴이 서로의 대조군이 된다. rollout의 `turn_context`로 턴 경계를
확정하고 턴별로 셌다.

| 턴 | `approvals_reviewer` | exec 호출 | MCP 호출 | 도구를 지목받았나 |
| --- | --- | --- | --- | --- |
| T1 (04:47Z) | `user` | 56 | **9** (전부 `getGuideDocument`) | **예** |
| T2a (05:27Z) | `auto_review` | 0 | 0 | 아니오 (즉시 전송사) |
| T2b (05:30Z) | `auto_review` | 23 | **0** | 아니오 |
| T3 (05:58Z) | `auto_review` | 진행 중 | — | 아니오 |

턴별로 exec 셀을 분류해 세면 이렇다. (T1의 MCP 셀 7개가 호출 9회인 것은 한 셀이
`["PRODUCTION_DESIGN","WORLD_DESIGN"]`처럼 이름 배열을 돌기 때문이다.)

| 턴 | exec 셀 | MCP를 부른 셀 | `shell_command` 셀 | `node_modules/@automovie` 를 읽은 셀 |
| --- | --- | --- | --- | --- |
| T1 | 56 | **7** (호출 9회) | 39 | **12** |
| T2b | 23 | **0** | 23 | **20** (87 %) |
| T3 (중단 시점) | 32 | **0** | 22 | 8 |

**여기서 이분법을 버려야 한다.** 도구를 9번 쓴 T1조차 같은 턴에
`node_modules/@automovie/**`를 **12번 읽었다.** 즉 가이드 표면은 소스 읽기를
**대체하지 않는다.** 지목받으면 *추가로* 쓰는 채널일 뿐이고, 지목이 없으면 그 채널만
사라지고 소스 읽기는 그대로 남는다.

**T2b의 23개 exec 호출은 전부 `tools.shell_command`였고, 그중 20개가
`node_modules/@automovie/**`의 제품 소스를 읽었다.** 무엇을 읽었는지가 핵심이다 —
`realizeShotContract.ts`, `stageScene.ts`, `blockBeat.ts`,
`AutoMovieProductionCompiler.ts`, `IAutoMovieProductionCompiler.ts`,
`requiredSubjects` 정의, `IAutoMovieVideoEdit` 정의. **전부
`getGuideDocument`의 `SHOT_CONTRACT`·`TYPESCRIPT`·`COMPILATION` 가이드가 답하는
질문이다.** 같은 세션이 바로 전 턴에 그 도구를 9번 성공적으로 불렀는데도 그랬다.

> **[2026-08-18 정정]** 이 문단이 끌어내는 결론의 근거는 위
> 「정정」 절에서 철회됐다. 이 계수는 *갖고도 안 썼다* / *없어서 못 썼다* /
> *불렀는데 거절당했다* 세 상태를 구별하지 못한다.

**다만 T2b 시점에 서버가 실제로 등록돼 있었는지는 `unverified`다.** 등록은 호출
단위 플래그로 들어가는데, 전임의 턴 2 실행은 인라인이었고 그 트랜스크립트가
남지 않았다. rollout의 `world_state`와 `thread_settings_applied` 어디에도 **MCP
서버나 도구 목록이 기록되지 않는다** (확인함: `world_state`의 상태 키는
`agents_md, apps_instructions, environments, host_skills, model, permissions,
personality, plugins_instructions, realtime, skills` — 도구 표면이 없다).

그러므로 T2b의 0건은 **"갖고도 안 썼다"와 "없어서 못 썼다"를 구별할 수 없다.**
로그에서 둘은 똑같이 0으로 보인다. 이것을 기록해 두는 이유가 그것이다.

확실한 것만 남기면 이렇다.

- **도구는 이 세션에 실제로 제공됐고 정상 동작했다** — T1의 9회가 증명한다.
- **호출 단위 등록은 실재하며 서버 프로세스를 띄운다** — T3 실행 중 실측했다.
  `node .../ancient-civic-temple/node_modules/tsx/dist/cli.mjs .../scripts/mcp.ts`가
  codex의 자식으로 살아 있었다.
- **`codex mcp list`에는 이 서버가 처음부터 없다.** 전역 레지스트리에 쓰지 않는 것이
  격리 설계이고, 전역 등록은 다른 캠페인이 소유한 공유 설정을 건드리는 일이다.
  T1이 부른 심볼이 `tools.mcp__automovie_ancient__getGuideDocument`로 **밑줄**
  이름인 것이 그 증거다 — 전역 목록의 이름들은 전부 하이픈이다.
  **전역 목록에 없다는 것을 "사라졌다"로 읽으면 안 된다.**

### 왜 그런가 — Codex가 code mode로 돈다

MCP 도구가 네이티브 도구 호출이 아니라 **실행되는 코드 셀 안의 함수**로 노출된다.

```
tools.mcp__automovie_ancient__getGuideDocument({ name: "WORLD_BUILDING" })
tools.shell_command({ command: "rg -n ... node_modules/@automovie" })
```

**둘이 같은 namespace의 형제다.** 가이드를 부르는 비용과 셸을 부르는 비용이 같다.
마찰 차이가 없으므로 "비싼 크레딧 경로를 피한다"는 설명은 이 데이터로 지지되지
않는다. 지목하면 쓰고, 안 하면 **셸로 제품 소스를 직접 읽는다.**

`approvals_reviewer` 가설도 이 세션은 **지지하지 않는다.** MCP를 실제로 쓴 유일한
턴이 `user`였고 `auto_review` 턴들이 0이다. 상관이 예측과 반대 방향이다. 다만 지목
여부와 등록 여부라는 교란이 겹쳐 있으므로, 옳은 결론은 "`auto_review`가 원인이
아니다"가 아니라 **"이 세션의 데이터로는 구성이 설명이 되지 못한다"**이다.

**T3도 깨끗한 대조군이 아니다.** 후임 드라이버의 턴 3 메시지가 열람 범위를 적으면서
`getGuideDocument`를 이름으로 언급했다. 사용을 지시한 것은 아니지만 이름이 다시
등장했으므로, T3의 결과를 "지목 없는 조건"으로 셀 수 없다. **지목 없는 조건을 재려면
그 이름이 한 번도 나오지 않는 턴이 필요하다.**

**제품에 대한 함의.** 가이드 표면의 가치가 `node_modules`가 통째로 읽힌다는 사실과
경쟁한다. 저작 에이전트는 `SHOT_CONTRACT`를 물어보는 대신 컴파일러 소스를 읽어
같은 지식에 도달했다. 이것이 "관찰 표면 > 배송 표면"이 실제로 무는 지점이다.

### 진행 상태 — 두 턴, 약 90분, 기하 0

- **턴 1** (13:47→14:38, ~50분): 문서 사다리 + 표면 분해. 전송 손실로 중단.
  디스크에 남은 것: 문서 21개, `src/world/` 22개. 컴파일 exit 1, 진단 29.
- **턴 2** (~40분, 418,410 토큰): starter 영화 → 신전 이주. 전송 손실로 중단.
  디스크에 남은 것: starter 소스·문서가 **실제로 삭제**되고 신전 것으로 교체됨.
  컴파일 exit 1, 진단 **29** — 개수가 줄지 않았다.

**두 턴 모두 인프라 손실이다.** `stream disconnected before completion`,
`Reconnecting... 1/5..5/5`. 저작 실패가 아니다. 두 번 다 디스크에서 산출물을 확인한
뒤에야 이 판정을 내렸다 — 로그만 보면 "아무것도 못 냈다"로 잘못 기록된다.

### 막힌 지점과 그때 제품이 준 진단

**제품이 준 것 (긍정).** 컴파일 오류 18건이 **전부 대상·파일·시정 조치를 이름으로**
말했다. 절반만 이주된 상태가 진단만으로 완전히 읽혔다 — 원인을 알기 위해 소스를 읽을
필요가 없었다. 예: `acceptance "opening-pose"가 없는 claim "cue-arm-readable"을
인용합니다. 수정하거나 claim을 추가한 뒤 다시 컴파일하십시오.`

**제품이 길을 주지 않은 것 — 증거 의무의 양방향성.** 스타터 교체가 **전부 아니면
전무**다. 증거 의무가 문서→소스 양방향이라 스타터 문서를 지우면 스타터 소스가
빌드를 깨고(클래스 10개 `cites 0`, `Unresolved evidence target` 약 45건), 그 역도
같다. 결과로 **"문서 전용 단계"를 초록 빌드로 닫는 것이 원리적으로 불가능**하다.
전임의 S0 종료 조건이 그 때문에 성립하지 않아 턴 2에서 정정되었다.

같은 덫이 **세 번째 층에도 걸려 있다.** 턴 2가 `docs`와 `src`를 옮겼는데
`automovie/design`은 그대로 스타터다 — `shots/{opening,answer}.json`,
`acceptance/{opening,answer}-*.json`, `shared/models/{soloist,chorus-*}.json`,
`shared/formations/chorus.json`. 현재 컴파일이 아직 shot `opening`과 claim
`cue-arm-readable`을 인용하는 이유가 이것이다.

**저작자가 스스로 한 것 (긍정).** `buildingDimensions.ts`에
`assertTempleDimensions`를 두어 **지붕 아래 총면적이 433.5㎡가 아니면 throw**하게
했다. 목표 430㎡ 대비 +0.8%. 외곽 깊이 21.5, 처마 4.2, 용마루 6.4, 주랑 유효폭 2.5,
외벽 0.5 m. 픽셀 비례가 아니라 동선·목재 스팬에서 유도했다고 스스로 적었다.
**기하를 세우기 전에 치수 불변식을 먼저 못 박은 것은 일의 순서가 맞다.**
(턴 1 중간의 25.0 × 22.0 / 426㎡에서 스스로 개정한 값이다.)

### 캠페인이 실측으로 확정한 환경 사실

- `npm`이 아니라 **`npm.cmd`**. `.ps1` 심이 `RemoteSigned` 실행 정책에 막힌다.
- `codex exec resume`에는 `-s/--sandbox`가 없다. 전역이 `sandbox = "elevated"`라
  `-c sandbox="workspace-write"`를 주지 않으면 **턴 중간에 모드가 조용히 바뀐다.**
- `codex exec`에 **`< /dev/null`**. 없으면 `Reading additional input from stdin...`
  에서 멈추고, 그 정지는 "긴 사고 중"과 구별되지 않는다.
- `codex exec resume`은 `-C`를 받지 않는다. `--last`는 서브에이전트 스레드로
  해석되어 실패한다. 프롬프트는 **stdin**으로 — `-i/--image`가 가변 인자라 뒤따르는
  프롬프트 인자를 삼킨다.
- `--approve-for-me`는 bypass 플래그와 상호 배타이고, 그 모드에서는 `npm` 자체가
  `PSSecurityException`으로 막혀 컴파일·렌더·검증이 전부 불가능하다.
- **세션 생존 판단에 mtime을 쓰면 안 된다.** 이 파일시스템에서 rollout이 88 KB
  자라는 동안 스탬프가 고정된 것이 실측되었다. 일차 신호는 프로세스 종료, 교차
  확인은 파일 **크기**.
- `capture:doctor`가 "실행 파일 서술자의 스탬프가 열려 있는 동안 움직였다"며 실패하면
  몇 초 뒤 **`capture:doctor`를 다시** 돌린다. `capture:install`을 재실행하지
  않는다 — 제품 자신의 메시지가 그렇게 말한다.
- codex의 MCP 등록은 **전역이고 전부 enabled**다. 격리하지 않으면 세션이 남의
  샌드박스에 쓰는 도구를 본다. 끌 목록은 손으로 박지 말고 **실행 시점에
  `codex mcp list`에서 센다** — 드라이버가 붙을 때마다 서버가 하나씩 는다.

### 이슈 본문과 실제가 어긋난 것

- `examples/era-reference-images/**`가 **없다.** 레퍼런스 5장은 이슈의 GitHub 자산
  URL에서 직접 받았다.
- `npm run status`, `npm run contribution`, `gltf` 스크립트가 **없다.** `status`는
  `review:status`로 읽었다. `contribution`은 대체하지 않고 `unverified`로 남긴다 —
  대체하면 다른 것을 재게 된다.
- **`derive:example`은 있다.** 이 줄은 원래 없는 것으로 적혀 있었고, 그것이
  틀렸다. 이 샌드박스의 `package.json`이 지금 나열하는 스크립트는 `capture:doctor`
  `capture:install` `build` `compile` `lint` `lint:source` `preview`
  `review:status` `render` `viewer` `test` `verify` `format` `design`
  `derive:example` `building:report` `texture:scale`이며, 세어 보면 답이 나오는
  주장을 세어 보지 않고 적은 것이 이 오기의 전부다. 추적되는 기준선의 틀린 줄은
  다음 사이클을 그대로 오도하므로, 지우지 않고 정정으로 남긴다.
- `internals/scorecard.mjs`가 없다.
- 이슈가 지목한 `renderer-verification` 스킬은 존재하지 않는 이름이다. 실제 스킬은
  `viewer-verification`.
- fal.ai 경로는 **사용자 지시로 취소**되었다. 자산 생성 없이 전부 코드로 짓는
  절차적 기하다. `.env`는 읽지도 넘기지도 않았다.

## 5. 판정

### 제품이 감당한 것

- **진단의 질.** 절반만 이주된 프로덕션의 상태가 진단만으로 완전히 읽혔다. 이것이
  이 실험에서 제품이 보인 가장 강한 성질이다.
- **정직한 거절.** `building:report`가 기하 0에서 "이 프로덕션이 무대에 올린 건축
  환경이 없으므로 그릴 것도, 셀 것도, 연구할 것도 없다"고 exit 0으로 거절했다.
  **알려진 0에서 정직하게 거절하는 것이 나중의 비-0 출력을 믿을 수 있게 만든다.**
- **`texture:scale`의 자기 서술.** starter에서 모델 4·부품 52 중 텍스처 좌표를
  가진 것 0, 검사 가능한 좌표 소스를 선언한 것 0이었고, 도구가 스스로
  "아무것도 측정되지 않았으며 이 실행은 texture-scale 리뷰가 아니다"라고 말했다.
  **exit 0을 초록으로 읽으면 안 되는 상태를 제품이 먼저 말해준다.**
- **결정론적 캡처.** `angle:swiftshader`는 조용한 소프트웨어 폴백이 아니라 제품이
  결정론을 위해 **요청한** 백엔드다. `capture:doctor`가 renderer 문자열과 실행 파일
  digest까지 영수증으로 낸다.

### 제품이 거절한 것과 그 정당성

**증거 의무의 양방향성이 스타터 교체를 전부-아니면-전무로 만든다.** 이 거절은
**정당하다** — 증거 그래프의 목적이 문서와 소스가 서로를 놓치지 않게 하는 것이고,
한쪽만 지우는 것은 정확히 그 그래프가 막아야 할 상태다.

다만 **비용이 스캐폴드 설계에 있다.** 스타터가 완결된 영화 하나로 심겨 있어서, 실제
프로덕션을 시작하려면 첫 걸음이 "전부 교체"가 된다. 저작 에이전트가 두 턴에 걸쳐
그 교체를 하느라 **자기 건물은 한 줄도 짓지 못했다.** 이것이 결함인지 의도된
설계인지는 이 실험이 판정할 것이 아니다 — 관찰로 남긴다.

### 측정 불가로 선언하는 축 (오염)

`HANDOFF.md`가 저작 세션에 **읽혔다.** 실측이다 — 세션 턴 1에서
`Get-Content -Raw -Encoding utf8 -LiteralPath "HANDOFF.md"`와 그 본문이 트랜스크립트에
있다. 원인은 부주의가 아니라 **구조적 충돌**이다: 캠페인이 `HANDOFF.md`를
`experimental/<name>/`에 두라고 요구하는데 그곳이 곧 저작 에이전트의 작업 루트이고,
같은 캠페인이 방법론은 감추라고 요구한다.

이 실행에서 다음 축은 **측정 불가**다.

| 축 | 이유 |
| --- | --- |
| `texture:scale` / `coordinateSource` | 핸드오프가 "exit 0은 아무것도 측정되지 않았다는 뜻"이고 좌표 소스 선언이 0이었다고 이미 적어두었다. 지금 프로덕션이 `coordinateSource`를 선언해도 발견과 상기를 구별할 수 없다 |
| 경계 준수 | `git status --porcelain`이 비어 있고 감시된다는 것을 알게 되었다. `experimental/` 안에 머문 것이 더 이상 독립 증거가 아니다 |
| 캠페인 이슈 결함 발견 | 없는 스크립트 목록·fal.ai 미배선·`scorecard.mjs` 부재를 통보받았다. 독립적으로 재발견할 수 없다 |
| 계측기 함정 인지 | 래퍼 종료 코드 함정과 `capture:doctor` AV 설명을 받았다 |

**회복 수단은 같은 브리핑으로 슬림한 핸드오프를 놓고 다시 도는 것뿐이다.**
14:1x에 `HANDOFF.md`를 운영 사실만 남기고 줄였고, 나머지는 작업 루트 밖으로 옮겼다.

부수 오염 둘.

- 세션이 저장소 SKILL.md 다섯 개(`project`, `evidence-graph`, `documentation`,
  `scaffold`, `development`)를 읽었다. 전임의 턴 1 메시지가 샌드박스 밖 열람을
  허용했기 때문이고, 턴 2에서 철회되었다. 더불어 Codex가 **14개 스킬 색인 전체를
  자동 주입**했다 — 샌드박스가 저장소 안에 있어 Codex가 git 루트에서 `.agents/skills/`를
  발견한다. 이쪽 절반은 요청하지 않은 것이다.
  **`.agents/skills/experiment/**`와 `.wiki/`는 읽히지 않았다.** 실험의 방법론
  문서는 새지 않았고, 저장소의 엔지니어링 관행이 샜다.
- `getGuideDocument` 사용은 전임이 그 도구를 지목했으므로 자발적 도달의 증거가
  아니다 (위 4절).

**저장소 전체가 읽힌다는 사실 자체도 기준선에 남긴다.** `workspace-write`는 쓰기만
제한한다. 따라서 **저작 에이전트가 관찰한 표면은 제품이 배송하는 표면보다 크다.**

### 아직 확인하지 못한 것 — 전부 `unverified`

- **시각적 주장 일체.** 렌더가 없고 이미지가 없다. 외관·절개·중정·제실·기록 구역
  캡처는 이슈의 완료 조건인데 **하나도 수행되지 않았다.**
- 공간 그래프 준수(모든 방이 연속 주랑에 문을 낸다, 단일 storey) — 기하가 없어 잴 수
  없다.
- 그룹 계층의 깊이와 비평평성 — 같은 이유.
- 7개 장면·비트·시퀀스의 극작 품질. 정독하지 않았다.
- `npm run verify`, `npm run contribution` 결과. 전자는 미실행, 후자는 스크립트 부재.
