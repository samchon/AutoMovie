# 정체성, 경로와 맥락

## 추적 가능한 진단 레코드 {#diagnostics-traceable-record}

각 진단은 표시 문구가 바뀌어도 같은 종류의 상태를 식별할 수 있는 안정된 identity와 이번 발생을 특정하는 실행 및 입력 identity를 가져야 한다. 사용자는 메시지 문장을 해석하지 않고도 같은 원인이 반복되었는지 비교할 수 있어야 한다.

### Identity의 의미 안정성 {#diagnostics-identity-stability}

한 진단 identity는 같은 실패 조건과 의미를 계속 가리켜야 한다. 원인, 판정 또는 교정 의미가 달라지면 새 identity로 구분하고, 폐기되거나 대체된 identity의 관계를 사용자가 추적할 수 있어야 한다.

같은 종류의 상태가 여러 위치에서 발생하면 종류 identity를 재사용하되 각 발생의 경로, 입력과 영향 범위는 독립적으로 남겨야 한다. 서로 다른 원인을 하나의 일반 오류 identity로 합쳐 사용자의 교정 판단을 막지 않아야 한다.

### 진단 Code 목록과 행동 참조 {#diagnostics-code-catalog-reference}

각 호환성 version은 발생 가능한 diagnostic code의 열거 가능한 목록을 제공하고, 각 code는 판정 조건, 관찰 값, 영향과 교정 행동을 설명하는 정확히 하나의 versioned behavioral reference에 연결되어야 한다. 각 reference는 사용자가 이용하는 지식 표면에서 code로 조회할 수 있어야 하며, 조회 결과는 source를 대신 수정하지 않고 사용자가 위임한 저작 에이전트가 적용할 교정과 재검증 범위를 설명해야 한다. 실제 전달된 code와 reference 목록은 같은 revision에 답해야 하며 누락, 중복, 알 수 없는 code 또는 stale reference가 있으면 진단 문서 집합을 complete로 표시해서는 안 된다.

### 경로와 영향 범위 {#diagnostics-path-and-scope}

진단은 문제가 발견된 값, 관계, 문서 구간 또는 산출물까지 모호하지 않은 경로를 제공하고, 그 경로의 기준이 되는 project, 장면, 요청 또는 외부 입력을 함께 밝혀야 한다.

영향 범위는 한 값, subject, 구간, shot, scene, 산출물, 요청 전체 중 어디까지 결과를 무효화하거나 제한하는지 나타내야 한다. 한 위치에서 발견된 원인이 더 넓은 범위에 영향을 주면 발견 위치와 영향 범위를 서로 구분해야 한다.

### 위치, 시간과 Subject 맥락 {#diagnostics-location-time-subject-context}

위치가 있는 입력은 파일 또는 문서 위치와 해당 구조 경로를 함께 추적할 수 있어야 한다. 시간에 관계된 진단은 film clock, frame, interval, event 또는 cue 중 사용자가 실제 저작 단위로 찾을 수 있는 맥락을 제공해야 한다.

Subject에 관계된 진단은 사람, 물체, group, camera, light, sound, effect와 산출물의 안정된 identity를 사용해야 한다. 표시 이름이 같거나 instance가 많아도 영향을 받은 대상을 구분할 수 있어야 한다.

### 심각도와 결과 영향 {#diagnostics-severity-and-outcome}

심각도는 문구의 어조가 아니라 결과에 미치는 영향으로 정해져야 한다. 치명적 상태는 요청 전체를 계속할 수 없게 하고, 오류는 명시된 범위를 무효화하며, 경고는 결과를 만들 수 있지만 검토나 교정이 필요한 위험을 알리고, 정보는 결과를 무효화하지 않는 상태와 선택을 설명해야 한다.

같은 원인은 같은 정책과 범위에서 같은 심각도를 가져야 한다. 사용자 정책이 심각도를 바꾸면 적용된 정책과 최종 성공 또는 실패 판정의 변화를 진단 결과에서 확인할 수 있어야 한다.

사용자 정책은 무결성, 보안 또는 필수 결과를 무효화하는 상태를 통과 가능한 경고로 낮출 수 없어야 한다. 허용 가능한 품질 기준을 조정하는 정책과 제품 계약을 위반하는 상태를 구분해야 한다.

### 원인, 관찰값과 기대값 {#diagnostics-cause-observed-expected}

진단은 실패한 계약 또는 확인하지 못한 조건, 관찰한 값과 기대한 값 또는 허용 범위를 구분해야 한다. 파생 증상만 보고하지 말고 사용자가 수정할 수 있는 가장 가까운 검증된 원인을 가리켜야 한다.

원인을 확정할 증거가 부족하면 추정을 사실처럼 제시하지 않아야 한다. 확인된 사실, 가능한 원인과 추가 확인에 필요한 정보를 서로 구분해야 한다.

### 교정 힌트와 재검증 {#diagnostics-correction-and-recheck}

교정 힌트는 잘못된 대상을 찾는 방법, 허용 범위, 충돌하는 선택과 안전한 다음 행동을 제시해야 한다. 입력을 바꾸기, 지원 범위를 선택하기, 예산을 조정하기, 외부 의존성을 복구하기 또는 검토를 수행하기 중 실제로 가능한 조치를 구분해야 한다.

교정 힌트는 자동 수정이 수행되었다는 뜻이 아니며 손실, 의미 변경 또는 보안 완화를 숨겨서는 안 된다. 다시 확인해야 할 범위와 이미 유효한 범위를 밝혀 사용자가 필요한 검증을 과소평가하지 않게 해야 한다.

교정이 원래 요청의 의미, 품질 단계 또는 보안 경계를 바꾸는 경우 그 변화를 대안으로 명시하고 사용자의 선택 없이 적용된 해결책으로 제시하지 않아야 한다.
